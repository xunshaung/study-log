# Agent：组成、运行与工程设计

> 依据：李博杰《AI Agent 入门》第 1 章；Hello-Agents 第 1 章

## 一、组成：模型、上下文、工具、Harness

Agent 是通过感知与行动和环境交互、朝目标推进的系统，不必然由大模型驱动。Hello-Agents 的反射型、基于模型、基于目标、基于效用四类智能体说明决策可以来自规则、模型或效用函数，学习元件也能叠加在这些架构之上。

现代 LLM Agent 的两个工程视角：

- **Agent = LLM + 上下文 + 工具**：模型负责理解与决策，上下文提供决策所需信息，工具提供观察与行动接口。
- **Agent = Model + Harness**：Harness 是 Agent 边界内、模型之外的运行与治理代码，负责上下文管理、工具接口、约束、验证与纠正。

![Agent 与 Environment 的闭环，以及 Agent 内部的 Model–Harness 结构](images/fig1-1.svg)

**环境不是上下文。** 文件、网页、数据库、用户属于环境；只有被读取并组装进上下文，模型才看得见。工具既能读取环境，也能改变环境。

任务环境可用 PEAS 规约：性能度量（Performance）、环境（Environment）、执行器（Actuators）、传感器（Sensors）。数字环境常是部分可观察、随机的、动态的，并且存在其他行动者。因此 Agent 必须依赖反馈，不能把最初的判断当成始终成立的事实。

## 二、运行：上下文、工具调用、反馈

消息式实现里，上下文由五部分组成：系统提示词、工具定义、用户消息、历史模型回复、工具结果。最简单的追加式实现可写成 **上下文 = 静态前缀 + 轨迹**；生产系统还会检索资料、按需加载工具、压缩历史。

![多币种汇总任务的 3 轮轨迹](images/fig1-4.svg)

*图中轨迹需加上静态前缀（系统提示词 + 工具定义）才是完整上下文。*

工具调用的过程：给出工具说明 → 模型输出调用请求 → Harness 校验并执行 → 结果回填 → 模型决定下一步。**模型生成的是请求，不等于操作已经发生。**

ReAct 把推理与行动交替组织：思考 → 行动 → 观察 → 再思考。Hello-Agents 的旅行助手先查天气，再用天气结果查景点，最后生成建议。构成闭环的是反馈影响后续决策，不是机械重复调用。

消融实验一次去掉一个组件：

![实验 1-1 上下文消融实验设计](images/fig1-3.svg)

- 去掉工具定义：模型不会沉默，会给出格式工整、语气笃定的答案，内容来自参数记忆。
- 去掉工具结果：Agent 反复重试直到耗尽迭代预算。
- 去掉思考过程：代价小，因为"为什么这么做"常能从工具结果重建。
- 去掉历史记录：重复劳动、重复犯错。

结论：组件并不等价，判断标准是这条信息能否从别处重建；结论也不能脱离模型、任务与实现条件。**给出回答不等于完成任务**——上下文残缺时的典型失败不是报错，而是一份挑不出毛病的答案。

![自主 Agent 的执行循环与退出条件](images/fig1-6.svg)

循环必须自带停止条件：任务完成、输出 final_answer、模型不再调工具、错误次数超限、达到最大轮次。人工干预的触发点：超过失败阈值、涉及高风险或不可逆操作。

## 三、能力更新的三个层次

![图 1-2 Agent 能力更新的三个层次](images/fig1-2.svg)

| 层次 | 更新什么 | 特性 |
| --- | --- | --- |
| 任务内上下文适应 | 当前上下文中的示例、状态、检索结果 | 即时、低成本；任务结束后不自动保留 |
| 跨任务外部产物更新 | 知识文档、Prompt/Skill、程序与 Harness | 跨任务持久、可审计；依赖检索或工具调用生效 |
| 模型参数更新 | 模型权重（SFT、偏好训练、RL） | 高维能力、广泛泛化；训练与回归成本高 |

三者协同：**上下文负责临场适应，外部产物负责可控积累，参数负责内化难以显式表达的能力。**

预训练给出语言能力与世界知识，后训练（含监督微调、强化学习）进一步改善指令遵循与任务策略。**Agent 的行为改变不只发生在训练阶段。** "模型即 Agent"指模型把工具调用策略内化为原生能力，内化的是决策能力，不是把工具、执行环境和权限检查装进参数。

## 四、从提示工程到 Graph 工程

| 工程视角 | 关注什么 |
| --- | --- |
| 提示工程 Prompt Engineering | 优化输入给模型的自然语言指令 |
| 上下文工程 Context Engineering | 系统管理模型能看到的所有信息：系统指令、工具定义、对话历史、外部知识 |
| Harness 工程 | 从"模型能看到什么"扩展到"Agent 如何组织模型运行并与环境交互"：上下文与工具接口、约束、验证、反馈循环、错误恢复 |
| Loop 工程 Loop Engineering | 从单次运行扩展到跨轮次持续自主运转：谁发现下一件事、何时验证、何时算真正完成 |
| Graph 工程 Graph Engineering | 把 Agent 循环、确定性程序和人工审批组织成显式执行图：节点承担能力，边规定路由与依赖，结构化状态沿边传递并在关键边界持久化 |

五者层层包含，不是替代关系：提示工程 ⊂ 上下文工程 ⊂ Harness 工程 ⊂ Loop 工程 ⊂ Graph 工程；单个 Agent 循环正是执行图中的一个节点。Graph 工程是 2026 年 7 月业界开始使用的名称，相关实践早于名称（LangGraph、Microsoft Agent Framework、Google ADK 的文档称其为图编排或 graph-based workflow）。

## 五、工程视角：Workflow 与可靠性

![Workflow 和 Agent 的差异](images/ha-workflow-vs-agent.png)

Workflow 用预定义代码路径编排 LLM 和工具，执行路径确定，LLM 只在节点内部理解和生成；自主 Agent 的路径当场根据反馈决定。前者顺序不被跳过、影响面受限，遇到未预设的情况会卡住；后者能处理开放问题，代价是成本与复合错误风险。部署顺序：先优化提示词，再上工作流，最后才引入自主 Agent。

Harness 的五项职责：

| 职责 | 干什么 |
| --- | --- |
| 上下文管理 | 决定这一轮给模型哪些信息 |
| 工具接口 | 把行动请求变成真实调用 |
| 约束 | 限定能做什么，默认关闭、显式开放 |
| 验证 | 检查结果对不对 |
| 纠正 | 静默重试、接续生成、连续失败时熔断交给人 |

护栏按被绕过的难度分三层：上下文层（管进入模型的信息）、执行层（管动作与权限）、数据层（用数据库权限、约束与校验器保证最终状态）。多个护栏组合才构成防线，**结构化数据不自动可信，固定工作流也不自动免疫提示注入。**

五个可复用设计模式：提议者—审核者、渐进式披露、只增不改、边界集 + 保留集、最小 diff + 可回滚。

行业重心正从"能做事"（上下文与工具）转向"可靠地做事"（约束、验证与纠正）。Claude Code 的 Harness 中，流程状态管理、多层上下文压缩、权限分类、熔断器、错误恢复占了绝大部分代码，工具本身只是一小部分。LangChain 在 Terminal Bench 2.0 上把得分从 52.8% 提升到 66.5%，改变的不是模型而是 Harness。
